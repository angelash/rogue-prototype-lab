日期：2026-11-19｜版本：v1.0｜对象：当前本地 Unity 2022.3.62f3c1 还原工程及 iteration-14 Windows 候选。

结论：可以沿现有 Unity 工程做手机化，已有触屏基础值得复用；发布微信小游戏仍需一次明确的平台移植，当前不能直接切 WebGL 打包上线。 最先处理的是版本/能力判断、战斗指针语义、触摸事件归属、Steam 编译边界、首场景资源依赖和存档持久化，然后才是纹理/音频/渲染优化与正式包验收。

用户所说“微信小程序包”，在这个游戏的技术路线中应落实为微信小游戏类目应用与小游戏包。采用 Unity → WebGL/Wasm → 微信官方转换 SDK 的链路；不是生成 APK/IPA，也不是把 Windows EXE 或一个普通小程序网页上传。沿用已确认的微信先行、抖音随后和已取得商业改编授权的方向，授权范围仍待私有留档。

1. 本次工程基线：比上一份发行计划前进了一步

2026-11-18 的发行计划归档时，完整核心循环尚待整合。2026-11-19 当前记录已有 Windows 原生鼠标操作证据：第一章胜利、第二章循环、商店/收藏、说明、设置、制作人员页及正常退出续档；iteration-14 另修复商店图集，定向构建0错误/0警告、运行0 error/exception。完整核心验收属于 iteration-12/更早明确版本，iteration-14 不是全游戏重测。[E01]

本轮把 iteration-14 的 source-before.json 中 2,337 个登记输入文件与现有工程逐项 SHA256 比对，没有缺失或差异。这些是登记范围内的源码/设置等输入，不能推成全部资产、所有后期、听感或微信功能已验收。当前静态扫描在 Assets 下数到 2,277 个 C# 文件，其中主游戏目录 727 个；它与还原队列的“类型数/方法数”不是一个统计口径。[E01][E02]

另已读取最新第二阶段接续文档；它正在安排阶段一私有交付与微信技术纵切。本报告补充工程分析，不把接续清单或远端交付安排当作微信开发已经执行，也不代替其它会话的交付收据。[E01]

已核对的技术基础：

  • Unity 2022.3.62f3c1；本机 WebGLSupport 目录存在，尚未运行它完成本工程构建。
  • 包依赖含 uGUI 1.0.0、TMP 3.0.7、Input System 1.14.0、UniTask 2.5.10，以及 Steamworks.NET；DOTween 为项目内托管 DLL。没有发现微信 SDK 或 Addressables 的工程文件/依赖配置。[E03]

2.1 必须先拆开“发行版本”和“设备能力”

GameVersionManager.Awake 在所有非 Editor Player 中把 currentVersion 强制设为 FullSteam，而 IsAndroid/IsIOS 仅检查原版本枚举。微信导出是 WebGL/Wasm，即使运行在 iPhone/Android 微信里，也不能期待它走 FullAndroid/FullIOS。[E06]

这会影响初始输入类型、光标偏移、版本 Gate、移动设置与平台入口。建议分开维护：发行平台（PC/微信/抖音）、运行设备/输入能力（触屏/鼠标/手柄）、内容权限（已授权内容）和服务能力（广告/云档等）。不要为了启用触屏把整个游戏伪装成原生 Android 付费版，也不要只把枚举改成 FullWeb 就假定所有 Gate 正确。

执行改动：建立独立微信配置和平台编译条件，PC 原行为保留；审计 GameVersionGate 的激活表，逐项决定手机界面、Steam/DLC、设置、引流/付费入口和调试对象。用正式 Player 验证首帧就按触屏初始化，而非等第一下触摸才切设备。微信PC端或外接鼠标的支持范围另列，不通过伪造输入类型覆盖所有情况。

3. 手机点击操作：具体要改什么

3.1 战斗不是“每点一下攻击一下”

当前 InputHandler.GetPointerPosition 提供单个指针坐标；CursorDamagePerSecond.Update 在 Survive 等资格满足时按时间间隔持续 ApplyTick，并未要求手指/鼠标按钮保持按住。它的命中范围还能涉及怪物、英雄治疗、卡包、盒、法典、宝石、消耗品和特殊场景物件。改成点击攻击会改变攻击频率、开包速度和成长收益，不属于单纯 UI 适配。[E07][E08]

建议首个手机候选：在战场空白/有效世界目标上按住时激活战斗指针，单指拖动连续瞄准，抬手或 cancel 停止。 Tick 间隔、伤害、半径先保持规则原值；只改变触屏指针的有效期，并记录这是相对 PC 悬停的输入行为差异。可另比较“点击后锁定位置持续生效”的辅助模式，但后者会改变挂机程度，不自动作为同一规则放行。

必要细节：

  1. 每次接触建立手势身份，保存 pointer/touch ID；第二根手指不能接管战斗坐标或把 UI 的第二次点击传给战场。
  2. 按下时先判断 UI、弹窗、教程遮罩、技能树和广告是否拥有此手势。被 UI 接管的按下，直到抬手都不能转成世界攻击；手指拖离按钮也不能“穿透”到战场。
  3. 统一记录开始/移动/结束/取消和当前有效位置。抬手、触摸取消、切后台、广告打开、系统菜单、失焦、场景退出都清除战斗资格及历史轨迹；恢复后须新的明确操作，不在旧坐标继续伤害。
  4. 所有坐标都经同一条屏幕→CRT映射/偏移→世界转换链，视觉圈、实际命中与预览提示共用结果。当前 CursorDPS 使用了移动偏移，UI CRT remap 又是另一入口，要核对一次且仅一次变换。[E08][E15]
  5. 手指遮挡建议提供可设置的上方偏移和可见瞄准圈；现有偏移以世界单位定义，并按横向位置调整，不能直接当“固定半厘米”或逻辑像素使用。缩放、画幅变化后保持视觉与碰撞一致。

建议先定义输入状态：Idle → UI手势或世界手势 → 移动/按住 → Released；任意时刻 Cancel → Idle。普通点击、世界持续指针、技能树缩放分别消费这份状态，避免每个系统再各自监听 Touchscreen.current.press。

3.2 商店、技能树、收藏：详情与提交分离

目前二次触摸式代理已经考虑了手机没有悬停，但它们在 UI pointer-up 和按钮回调之间还有组合行为，不能再全局补一层“触摸模拟鼠标点击”。建议：点击卡包/节点/收藏卡打开固定位置的详情面板，动作按钮明示“购买/升级/设为目标”等实际含义；点空白或返回关闭。若保留二次点击，第一次必须给明显选中态，第二次动作和资源扣除在界面上写清。

重点防四类误操作：拖动结束误购买、双指缩放结束触发升级、一个 Touch 生成 UI click 与业务 click 两次提交、购买动画/揭示中重复扣币。每个购买/升级命令由业务资格和事务去重处理，不能只靠按钮暂时变灰。[E09][E10]

技能树当前配置 minZoom=0.1、maxZoom=1，主树 cellSize=150，pinchZoomStep=0.0008。缩到最小时，网格间距只有15个参考单位，远小于可稳定触摸的尺寸；扩大每个热区会互相重叠。建议远景用于浏览，进入可交互缩放后再选节点，或提供“可升级项”列表/定位按钮。两指缩放期间取消待点击，结束时不能自动补一次购买；40个屏幕像素的旧位移容差应按实际 Canvas/设备坐标体系重新验证，不能当通用44逻辑像素热区。[E10]

收藏卡详情不能只在悬停期间存在；长说明滚动、换卡、WantedHunt 解锁条件与关闭路径都要触摸可达。动态生成的新节点/商店卡也要走同一输入契约，不能只适配场景中当前预置的代理。

3.3 过场、奖励动画和教程

部分屏幕的“任意输入”已有 Touch 分支，但仍使用 press.isPressed 这种持续状态，容易在同一根手指未抬起时跳过新出现的下一层动画。统一改为明确开始/结束边沿，打开界面时过滤唤起它的那次输入，只允许新动作推进。结算、工资、稀有开包、章节结束与首次教学应分别测试。[E11]

GuideStep 的非按钮目标点击/悬停路径直接读 Mouse；HoverInfoGuide 虽识别 primaryTouch，但部分命中判断仍用 Mouse 坐标。应改为“触摸选中并看到详情”或“执行成功动作”的业务完成条件。静态扫描未在序列化场景/预制件中找到 GuideStep 的直接引用，它可能属于未启用或后续路径，先确认实际使用再排优先级，不能把存在源码直接写成已阻断当前教程。[E11]

3.4 消耗品、返回、设置和文字输入

  • CardInHandUI 的点击可能直接 UseCard，而说明由 PointerEnter 打开；触摸用户可能还没读完就使用。默认改为点击先详情，再“使用/跳过”，与自然掉落即时选择共用一套规则，不因为手机新增无限暂停、额外资源或免费取消。[E12]
  • 保留当前 BackStack 的业务顺序，所有必要页面增加可见返回/关闭，不依赖 Esc、Space、手柄按钮或系统返回行为。输入框开着时，首次返回先收起键盘，第二次才关页面。
  • 桌面分辨率/全屏、Steam、DLC、在线兑换码传档、无效云服务设置按微信能力重新定义。当前离线恢复适配隐藏了部分原在线功能，它不等于微信平台实现。[E13]
  • 危险的删档操作保留长按或二次确认；补充多指、滑出、取消、切后台与连续重入时清除 hold 计时。不能因为手机容易误触把“重置”改成单击立即清档。
  • 当前 TMP 为3.0.7，但本工程是普通 Unity 2022，不能由版本号推出微信 TMP 输入法自动适配。官方输入法文档对普通 InputField 与 TMP/团结支持范围有区别，且自动适配默认关闭。必要的名字/客服输入走当前 SDK 支持的键盘能力，确认/取消/遮挡/长度/中文组合输入逐项验收。[W11]

3.5 不应误判为当前核心阻断的源码

CastSpellManager.Update 直接读鼠标左键，但场景中该组件 m_Enabled=0。SlashDetector 源码按相邻指针位置和速度判断划切，本轮没有找到它在场景/预制件的序列化引用，也没有找到显式 AddComponent 调用。这些是后续功能恢复/启用前要适配的债务，不能据此宣称当前手机主流程一定已出错。[E14]

若后续启用划切，触摸开始必须重置前一点，不能把“两次在不同位置点按”当作连续高速挥砍；touch ID 改变、UI拦截和cancel均断开轨迹。划切与持续光标的规则资格要分别验证，不用一条全局 touch→mouse 映射解决。

4. 屏幕、点击区域与画面布局

当前有三个主要 CanvasScaler 按1920×1080缩放、matchWidthOrHeight=0.5；教程 Canvas 和平台 Canvas 则是 Constant Pixel Size。SafeAreaFitter 只用 Screen.safeArea 改锚点。现有 PC 截图上，商店长期占左侧约三分之一，右侧同时放技能树/密集收藏网格，右上还有设置等小按钮；等比例缩小到手机会明显压缩说明和节点的可触摸空间。[E06][E16]

建议首候选仍横屏，避免在已有战场上同时承担竖屏重新布局的成本。不是只把宽高改成手机分辨率：

  1. 商店做可折叠抽屉、页签或上下文面板，技能树/收藏在触摸详情时获得足够面积；战斗按钮、资源和返回保持稳定位置，拇指不遮住关键信息。
  2. 交互热区以44–48逻辑像素作为起始设计建议，再做真机验证；美术可保持像素风，透明热区独立扩大但不得重叠。文字以最终逻辑尺寸验收，不把1920参考画布上的字号当手机字号。
  3. 首先覆盖16:9、19.5:9、20:9、4:3，以及较小横屏窗口；安全区、菜单胶囊/系统遮挡和可见内容区域分别处理。长屏不通过偷改战场规则范围或扩大攻击半径来“填满”。
  4. 微信官方要求用 WX.GetWindowInfo 获取安全区；其坐标以左上为原点，与Unity坐标及pixelRatio存在换算。按实际渲染分辨率/Canvas匹配关系计算比例，不能在 SDK 已转换后的坐标上重复乘DPR。窗口变化、旋转/恢复、折叠屏或微信窗口变化后重算。[W07]
  5. 世界相机、屏幕点击、CRT失真、手指偏移和UI射线测试统一校准：在边角显示标记并验证点中同一目标。关闭CRT时也须确认输入映射同步关闭；手机默认弱化扫描线/失真可提升文字可读性，并减少GPU开销。[E15]

验收必须用真实触摸。 编辑器鼠标和开发者工具可用于布局预查，不能证明触摸ID、系统取消、宿主键盘、胶囊遮挡和后台恢复正确。建议拍摄/记录设备、微信与基础库版本、逻辑/渲染分辨率、输入事件和业务结果，不只交一张截图。

6. 纹理、图集与Shader的处理方案

6.1 分类型导入，保留商店换色例外

普通背景、单位、图标分别设置移动纹理格式、最大尺寸、滤波、mipmap与读取权限。大背景先评估裁边/降分辨率；像素单位优先保留Point采样和必要边距。透明图集压缩要检查细线、透明边、SDF与缩放，不采用“所有图统一ASTC 8×8”作为全局完成标准。[W05]

UI_Elements.png 必须列为明确例外。 上一轮已证明有损BC7改变原RGBA32颜色，导致商店状态换色漏掉62个像素。当前320×320图集已恢复无压缩，WebGL等导入项也维持不压缩；其RGBA32单层仅409,600字节，约0.39 MiB，应优先保正确，不能移植时再次批量压缩回去。[E17]

ColorKeySprites 还会把图集局部 Blit 到 RenderTexture、ReadPixels、创建RGBA32纹理和Sprite，再CPU改色并保留缓存。它会带来GPU同步和额外副本，不是只调Importer就消失。候选方案按优先顺序比较：预制有限状态变体、改为可验证的调色Shader、或保留小范围换色缓存并限制生命周期。每种都要用实际图集逐像素/允许误差验证，不能仅保证“没有异常”。[E17]

源目录存在3840×1792的Aura图以及512×4384的图标图集等大尺寸源图；Importer可能缩放或重编码，不能把原尺寸直接当运行纹理尺寸。拆图集时保持Sprite GUID/切片映射、pivot、border、PPU、动画帧顺序、引用与透明留边。需要改变GUID时做明确迁移清单，不先删除或重新导入全部图片。

官方文档区分Unity原生压缩纹理与微信纹理分离工具；当前Unity2022可先验证原生方案，是否使用微信按设备分离再由真机内存决定。Android可比较ETC2/ASTC，iOS以SDK与设备支持为准；开发者工具/PC微信的软件解压行为不能作为手机GPU内存结论。纹理工具与导出SDK版本应一致，不混用旧压缩产物。[W02][W05]

6.2 Shader与渲染路径

恢复工程的自定义Shader已有CG/HLSL源，不是只能运行原DX11字节码；因此不应笼统说110个Shader必须全部重写。原98/106程序对应记录主要证明Windows路径，不证明WebGL2/GLES跨编译、精度、动态分支和手机显示已通过。[E15]

逐材质测试Sprite、剪裁/Mask、TMP、闪卡、溶解、光环、线条、屏幕效果和透明叠层。GraphicsSettings中存在大量Always Included项，要按本版实际使用及动态 Shader.Find 建清单，控制变体与预热；不能盲目全部保留，也不能只按静态场景删除动态使用项。

当前 Main Camera 启用了CRT失真和扫描线，CrtScreenFilter.OnRenderImage 执行全屏Blit。建议手机低档默认关闭或简化CRT，限制渲染分辨率/DPR，并检查所有后处理、透明特效与额外相机；先测GPU帧时和文字可读性，不把桌面帧率直接换算成手机60帧。保持Built-in先跑通，换URP作为另一个项目决策评估。[E15]

7. 音频、字体与内容数据

7.1 音频

已有394个OGG。最大的一个源文件约14.02 MiB、232.46秒、44.1kHz双声道；若全量解码为float32 PCM，单曲理论约78.21 MiB。这个值是探针参数的乘法估算，不是已测微信实际音频内存。[E18]

音频分为启动/首局必需SFX、公共短音效、各章BGM与环境循环、后期内容。保留原源，制作移动派生并记录转码参数/哈希；长音轨采用按需加载和及时释放，不让SoundManager及配置一次持有全部章节音轨。UnityAudio路径尽量复用，官方适配会按音频特点使用InnerAudio/WebAudio，不需要把SoundManager整体重写。[W06]

官方推荐mp3/aac双端兼容，但不能只把OGG扩展名改掉，也不必在未测试前批量转码394条。先做短SFX、长BGM、无缝循环、pitch变化/多源重叠四类样件；Importer与SDK导出结果确认后再量产。限制同时播放数，验证静音开关、蓝牙/来电、前后台、广告进出与循环接缝；当前Windows非零数字音频观察不替代手机听感。

7.2 字体与本地化

首发以中文及必要拉丁字符为目标，源工程中的日/韩字体和对应Logo作为可延期资产候选。先依据真实BuildReport/UsedAssets和运行加载路径确认是否被打包；本轮GUID扫描没有把所有Noto源字体都归入主场景闭包，因此不能把38.12 MiB字体源文件全算成可直接节省的包体。[E19]

检查TMP FontAsset、材质、Atlas、fallback链、动态造字和源码字体是否一起带入。为中文UI、规则文案、数字/符号、动态英雄名准备可复现字集；静态字集可削减首包，但运行输入/未来文案需要受控fallback，不能用精简字体引入缺字。官方QA建议控制中文首资源字体体积，具体2–3MB建议不是本作已达到结果，也不是适用于所有字库的硬限制。[W12]

LocalizationManager在Awake调用Resources.LoadAll读取全部CSV。文本表当前体积小，首阶段可保留，收益不如音乐/大资源；后续可生成中文发布表并保留稳定key、格式变量、备选文字与版本，不把删语言列当完整本地化验收。[E19]

7.3 配置数据与Resources

Resources目录含Sentis计算资源和TMP公共资源。先建立“确实用于启动/首局”“运行按名加载”“未使用恢复残留”清单，将确认不需要的恢复残留从移动候选移走并保留原工程/原始资料。WebGL普通图形路径不能直接沿用桌面ComputeShader，但是否有需要保留的模型/替代计算必须先查证，不能仅凭文件名自动删除。[E20]

ScriptableObject的直接引用会把图标、音轨、预制件一起拉入依赖。建立稳定内容ID/目录，将跨章节媒体引用改为异步可解析的资源句柄；已加载对象和保存数据仍引用同一内容ID。不能把Resources文件夹改名后所有 Resources.Load 继续返回null，也不能同时把同一图集放首资源和多个Bundle重复打包。

8. 首包、AB和CDN：需要真正改加载路径

当前Boot→SampleScene是Build index加载，SampleScene把大量系统和内容串在一起，项目没有现成AB/Addressables拆包。只把Boot勾选留下，而不改BootLoader/LoadingScreen的build index，就会失去主场景；把主场景挪到CDN但仍 LoadSceneAsync(1) 也不会自动从网络加载。[E05]

建议最小资源分组：

分组内容加载/释放边界
Bootstrap微信SDK、极简启动UI、错误/重试、版本与最小目录、必要中文进入即有反馈，尽量不引用章节内容
Shared UI公共UI/换色图集、必要字体、公共短SFX、详情面板首次需要时加载，严格控制长期驻留

Optional services广告、云档等平台能力与合法配置SDK先初始化，业务功能按资格启用

因为本作目前未使用复杂AA目录，建议先比较少量粗分组AssetBundle的最小方案；Addressables也可行，但需要新增包、远程Catalog、句柄/释放体系和额外索引，不能只安装依赖就算完成。微信官方提醒大型AA目录成本较高，选型以本作真实目录与加载结果决定，不把AB性能宣传当永远正确。[W04]

加载一律走兼容的异步网络接口或SDK路径。资源包存微信缓存，不仿照桌面先下载到 persistentDataPath 再 AssetBundle.LoadFromFile，也不默认Unity的浏览器/AA磁盘Cache能在微信等价工作。业务需要错误码、超时、重试、取消、低空间、依赖失配和回到上一步的路径；预下载不占满带宽阻塞首局。[W04][W09]

微信转换输出分两部分：minigame/为开发者工具导入/上传的小游戏代码与配置，webgl/中的首资源、分离纹理/音频及StreamingAssets等按实际方案部署CDN。Wasm代码分包、业务AB分包、首资源.data和微信代码包是不同东西。官方当前文档用“Wasm代码加包内首资源小于20MB”描述包内加载路径，不把它当全部资源总量、永久平台统一上限或本品已满足条件；执行时按锁定SDK和后台上传校验复核。[W03][W08]

CDN按不可变版本目录发布，如 bph/wx/<release-id>/...；Bundle与派生纹理文件名带hash，未带hash的Catalog/manifest要版本路径或明确不缓存。记录本次代码、内容目录、资源清单和存档schema的兼容关系；保留旧客户端需要的旧资源，发布后不要立即覆盖或删除。[W08][W09]

使用实际配置的HTTPS域名、证书、请求/下载合法域名、SDK相关插件权限和跨域规则；iOS高性能路径涉及的源站/CORS也要实测。文本/首资源的传输Brotli/gzip由SDK/CDN链路处理，防止重复压缩和错误Content-Encoding；不要照桌面WebGL教程直接打开Unity Brotli/Gzip选项。当前PlayerSettings的WebGLCompressionFormat原始值为1，官方QA要求微信路径保持Unity导出不压缩并由转换工具处理，需在独立构建Profile明确设置并回读产物。[E21][W12]

9. 编译、程序集与AOT

9.1 已有明确的平台编译风险

com.rlabrecque.steamworks.net 的Runtime asmdef只包含Android、Editor与桌面平台，不包含WebGL；FundayGames.PlatformService.Steam asmdef却直接引用它，业务的InputGlyphUtility等也直接使用Steamworks类型。仅让RestorationRuntime在运行时关闭DLC对象，不能解决WebGL编译阶段程序集缺失。这是静态可见的高优先级阻断风险，具体编译错误仍需执行独立WebGL构建确认。[E22]

建议：Steam实现程序集限定桌面目标；共享平台接口与微信实现分开；业务代码不得直接依赖Steam的类型。编译条件下隐藏/替换SteamInput、DLC、认证、成就、原UGS/Cloud与传档调用。用明确能力返回和UI说明处理不可用服务，不写一组“返回成功”的空实现假装上线能力。

UGS恢复程序集与UnityServices配置还在工程中，是否参与构建取决于引用和裁剪，不直接把名字数目当代码体积。先画程序集依赖、保留真正需要的接口；未经核实的分析、认证和云配置不带入微信业务版本。项目内托管DOTween DLL不同于原生DLL，不因后缀为.dll一律删除；须验证其AOT与反射/扩展模块使用。

9.2 WebGL构建需要单独的Profile

新增拟议入口（例如 MobileWechatBuild，当前尚不存在），与现有Windows构建分离。固定Unity版本、包锁、官方SDK tag/commit/哈希、产品/存档身份、平台define、WebGL/IL2CPP、异常与裁剪级别、纹理模式、Release/Debug、开发者工具基础库和Loader版本。配置必须可复现，执行结束还原/隔离桌面设置。

官方当前推荐列表支持Unity2022，但列出的已验证小版本为2022.3.1–2022.3.14；本机2022.3.62f3c1不在该逐小版本列表。先在隔离副本测当前版本，不据此判定不能用，也不擅自给活跃工程升级/降级。若遇已证实兼容问题，再比较替代引擎并保留迁移成本。[W01][W02]

当前WebGL原始设置为初始内存32、最大2048、线程关闭、异常支持1、压缩1。它们是未经过本作微信优化的序列化值，不是内存保证。以实际启动/局内/切图峰值设置Wasm堆增长，避免误将最大2048理解为可安全使用2GiB；总内存还包含JS、Wasm编译、纹理、音频和微信容器。[E21][W13][U02]

WebGL的C#路径要做AOT/裁剪检查：动态代码生成、反射、泛型实例、序列化、回调、JS互通与异步错误传递。只给确需反射保留项设置preserve/link规则，不能为编过把全部程序集永不裁剪。UnityWebRequest要yield/await，不使用阻塞等待；UniTask和协程可以沿用，但具体平台模块仍需编译/运行。[U01][W10]

扫描发现的大量 SkillTreeAnimationSpeed.Wait 是被 yield return 的协程辅助，不是已证实的线程阻塞；本轮没有在业务目录发现真实Task.Run/Thread.Sleep使用。线程检查的候选命中不能直接当bug数。观察/测试代码中Thread.CurrentThread、音频探针、自动输入和截图工具不进正式Player。[E23]

10. 存档、生命周期、广告和平台接口

10.1 保存语义可以复用，桌面写盘方式需要替换

GamePersistence保存schema为27，使用JsonUtility序列化后 File.WriteAllText(SavePath, json)，异常只记Warning；设置大量使用Unity PlayerPrefs。Windows正常退出/损坏档回退已有明确范围内证据，没有证明微信Storage/文件系统提交、清缓存或换机安全。[E13]

建议在现有业务快照之下加独立存储接口，采用微信可用的Storage/文件API并异步写入；资源缓存与不可丢的进度分目录、分生命周期。根据存档实测大小选择小键值或文件，不能先假定超过或小于某配额。当前官方文档提到Storage 10MB、默认文件缓存200MB和可申请空间提升等条件，不能当所有账号永久统一额度。[W09][W12]

最小可靠保存需要：版本/校验、上一有效代次、写入完成回执、失败提示、恢复选择与迁移样本。把奖励记录、资源变更和已领取事务一并提交；不能先显示领到奖励再静默写失败。手机可能被系统直接杀掉，不能只依赖OnApplicationQuit；关键购买/结算要及时形成检查点，广告/宿主隐藏前做轻量保存，后台长时间暂停后按产品规则恢复或提示。

如保留触屏每次开包/拖动即写盘，必须控制频率；不能每帧调用同步Storage。清理资源缓存时不删用户进度；若需要云档，用平台登录身份关联并处理离线、冲突、版本、重装及删除。当前离线UGS适配不是微信云档，不可直接上线宣传。

10.2 广告进出不能只靠Time.timeScale

新增广告接口在业务层管理资格与奖励；SDK回调只报告结果。显示广告时暂停输入、清触摸状态，冻结合适的结算/奖励机会；关闭/失败恢复后等待新的操作。CursorDamagePerSecond使用unscaledDeltaTime，单把timeScale设0不会自然停掉它，必须用明确的游戏/广告暂停资格阻止Tick。[E08]

区分用户取消、未完成、展示失败、无库存、超时、未知结果和明确完成；恢复前后台不等于看完广告。每次机会和回调去重，不把SDK创建或显示成功当奖励完成。是否支持服务端观看验证按当前广告位和SDK核实；服务端票据只能证明去重时，不宣称它能鉴定真实观看。广告位、频控、隐私、结算与资质更完整的商业要求仍见上一份发行计划。

10.3 微信服务适配

准备平台登录、合法云档、远程配置、广告、客服/隐私入口、分享和宿主返回能力。secret、session密钥和签名验证放服务端；前端AppID等公开配置与秘密分开。剪贴板、打开URL、文件导入导出、购买/跳转、输入法、震动等不能照搬桌面API；实际需要的入口逐项找当前SDK对应接口，不为迁移增加不需要的权限。[W10][W11][W12]

隐私允许范围与平台必要能力分开：非必要分析/营销处理在同意前不启动，拒绝仍可走基础游戏；不能把平台加载完成当用户同意。纯广告/随机包的审核边界沿上一份计划保留，但本次不扩大成新一轮法务结论或已完成平台申请。

11. 推荐执行顺序与可交付物

以下是工程检查点，不是本轮已经完成的移植。不从源文件大小推算开发天数，原145人日全链发行计划仍是历史估算；开始实施后以首个纵切测得的缺陷量重估。

  1. 冻结PC参考，开隔离微信副本。 保存当前可玩包、源码/设置/资产manifest与原存档隔离规则；不在正在使用的工程中直接切目标、重导全资源或覆盖还原脚本。还原装配脚本会重新落配置，移动改动要在明确维护的移动层，不做下一次装配即丢失的临时修改。
  2. 先通过无内容/少量内容的WebGL编译。 添加稳定SDK，解除Steam编译引用、修正GameVersion/能力和独立构建Profile；再接现有UI与必要业务。输出真实编译日志、错误清单、包清单和版本，不用PC成功作凭证。
  3. 打通一条真机可玩纵切。 新档进入→明确一次开包/奖励→战斗瞄准→胜负→结算→商店/节点说明与购买→退出/恢复。第一轮即覆盖UI拦截、双指、cancel和系统后台。
  4. 以实际BuildReport拆资源。 Bootstrap/共享UI/首局/后章节，清移动候选中的确认无用Resources；先做纹理、音乐、字体代表样件，比较首包、网络下载、解码与峰值内存。
  5. 接微信存储、生命周期与广告。 正常游戏保存先过，广告奖励再接；验证真回调、去重、后台返回和数据失败恢复，保留无广告路径。
  6. 做候选打包与发布演练。 锁SDK/Loader、构建WebGL内容与分组AB、导出minigame、上传不可变CDN资源、导入Stable开发者工具、真实AppID预览、双端测试、版本兼容与回滚，再按外部资质/审核流程形成可提交候选。正式发布和花费按实际授权执行。

  • Release不包含自动输入、观察探针、QA存档选项/作弊入口、调试服务器、测试广告配置和秘密；必要可控诊断另行设计。
