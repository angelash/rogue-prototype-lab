# 套圈改造摊：Steam 发行技术与交付方案

版本：v0.3；核对日期：2026-10-09（Asia/Shanghai）。用户明确选择 Unity、本机已有版本、PC 单机，并以 Steam 上架为目标。本文补发行准备合同；本轮没有创建 Steam 应用、支付费用、上传构建或发布商店。

技术基线见 [08 Unity PC](08-unity-pc-technical-plan.md)，资产生产见 [09](09-art-and-asset-production.md)，执行记录见 [10](10-development-workflow-and-skills.md)。下列实施顺序、平台可选功能和制作预算均为助手建议。

## 1. 首发交付边界

建议首发承诺 Windows 10/11 x64、离线单人、键鼠及完整手柄流程、简体中文游戏文本。Windows x64 + Mono 采用本机已具备的 Unity 2022.3.62f3c1 模块；最低硬件、下载体积和具体系统支持仍须在实际构建中测量。PC 不自动扩大为 macOS、Linux 或 Steam Deck 验证承诺。

发行物包括完整 Unity Player 目录、对应内容/参数版本、发布说明、操作与存档恢复说明、资产来源和许可证随包文件。商店声明以实盘为准：语言、控制器、云存档、成就等功能只有验收后才勾选。[Steam 构建审核规则](https://partner.steamgames.com/doc/store/review_process) 要求商店支持项与当前构建相符。

新局到十二摊、失败回流、练习/挑战、设置、暂停、退出和续局均应能离线完成。游戏运行期不调用生图或模型生成服务；AI 用于制作阶段的内容生产。

## 2. 游戏与平台服务接口

建议规则程序集不引用 Steam SDK。平台层通过一个薄接口提供可选平台身份、成就通知、覆盖层状态和存档命名空间；本地版本使用空平台实现，Steam 初始化失败也保留本地单机功能。

建议分期：

1. **纵切**：先交付可独立启动的 Windows 本地包，验证游戏循环、保存及输入。
2. **候选发行包**：取得真实 AppID 后验证 Steam 客户端安装、启动、关闭、覆盖层焦点与手柄路径。
3. **可选增强**：在成本允许时接成就与 Steam Cloud；未接通时不在商店承诺。没有联机、排行榜、交易市场和运行期 AI 服务需求。

若接 SDK，选择支持当前 Unity/Mono 的托管封装，确认其版本、许可证、native DLL 位数及官方 SDK 兼容关系后锁定。接入使用 Unity/C# 适配，参考工程的 Node/Web 依赖不进入 Unity Player。开发用测试 AppID 与本产品实际 AppID 区分，发行包清点开发配置和凭据；本稿不写入任何账号、API Key 或上传登录信息。

## 3. 构建、分发与版本

建议正式构建用固定内容版本、参数版本、Unity 版本及 Git 提交记录生成。Release 关闭 Development Build、脚本调试与自动连接 Profiler，保留可追溯构建信息；Development 包供 QA，二者分目录。

完整打包 Unity 输出目录，不只复制 `.exe`。确认同级 Player 依赖、数据目录及 Mono 运行时完整；依赖内容以构建清单核对，不能凭经验删除 DLL。日志、测试结果、缓存、生成原图、弃用素材、生产密钥和编辑器工具不进入发行包。

建议本地先生成构建 SHA-256 和文件清单，再创建 SteamPipe 内容目录：一个 Windows depot，启动配置指向实际相对路径的可执行文件。AppID、DepotID、分支名和上传目录由后台真实配置填入，模板不能当成已上传记录。SteamPipe 使用 app/depot 配置文件和受限测试分支验证下载后的一致性，记录 BuildID、源码提交、参数版本和包哈希。[官方上传流程](https://partner.steamgames.com/doc/sdk/uploading) 是后续命令与后台配置的依据。

上传完成后从 Steam 安装所得文件重新测试，不用编辑器 Play 或构建目录启动替代安装验收。正式发布采用已验证的相同候选包；版本变更重新记录差异与必要回归，保留可回退的旧 BuildID。

## 4. 输入、焦点与覆盖层

键鼠和手柄必须覆盖标题、瞄准、机关调整、商店、处置、设置、退出及坏档提示。默认将 Unity 动作输入作为主路径；Steam Input 的手柄映射先按模拟标准手柄路线验证，原生 Steam Input 动作集另作为后续选择。[Steam Input 官方说明](https://partner.steamgames.com/doc/features/steam_controller/getting_started_for_devs) 介绍模拟手柄和原生动作 API 两种方式。

验收直接连接和 Steam Input 启用两条路径；按键提示按实际设备/映射变化。设备断连、覆盖层或失焦暂停时，不遗漏正在结算的投掷、不额外消耗圈，不把返回游戏时残留的确认键解释为下一次发射。若覆盖层状态回调可用，接到与本地暂停相同的流程；仍验证系统切换窗口的兜底行为。

“完整手柄支持”以全部必要界面实测为准。文字输入若确实需要，提供可用手柄路径；本作不为没用到的姓名输入额外创建输入障碍。

## 5. 存档与可选 Steam Cloud

06 的事务提交记录、来源资格、领取去重和坏档备份继续为保存真值。游戏数据写入 `Application.persistentDataPath` 下的产品目录，不写安装目录或要求管理员权限；CompanyName/ProductName 在发行前固定，改名时保留旧档迁移。

首发建议先完成本地保存。Steam Cloud 可在实际双机验证后开启：只同步已提交的稳定存档和必要进度，排除临时写入、事务工作文件、可重建缓存、设备设置和大型轨迹历史。云上传不替代本地事务的原子性。

08 的本地保存由提交清单引用多个代次文件，云端不能只上传清单而遗漏依赖，也不能假定多文件同步是原子事务。建议在安全边界导出一份带提交序号、内容/格式版本、完整 Run/Profile 与校验摘要的云检查点；导入先验证整份检查点，再通过本地事务提交。Auto-Cloud 或 API 只传完整检查点及必要备份，具体格式与冲突流程在双机故障测试后锁定。

若启用平台账号存档，采用独立用户命名空间；离线默认档迁入平台档时显示两份进度与处理选择，不静默覆盖。冲突按有效版本、提交序号与玩家选择处理，不仅比较电脑墙钟时间。记录关闭云同步、断网、本地新进度、第二台机器以及账号切换后的结果。

[Steam Cloud 官方文档](https://partner.steamgames.com/doc/features/cloud) 提供 Auto-Cloud 和远程存储 API，并有 Unity persistentDataPath 配置示例。采用哪种方案需与上述文件布局共同验证；只有实际配置及双机测试完成后才声明支持。

## 6. 商店内容与宣传资产

建议准备中文短介绍、详细玩法、功能清单、操作说明、系统需求、支持邮箱/入口，以及清晰的主视觉与游戏标识。候选玩法标签围绕技巧投圈、单人、有限构筑和轻量肉鸽；最终标签与玩家定位在可玩版本确认后填写。

素材分为两类：

- **主视觉/胶囊**：可以用原创 Blender 场景或生图辅助构图，围绕圈、可改造旧物和河港夜市，不添加实际游戏没有的角色动作或机制承诺。标题由排版工具叠加，保留分层源文件和裁切安全区。
- **游戏截图/演示**：从实际 Player 录制，表现瞄准、机关改变轨迹、兑现/留场和回放。生图概念图不当作游戏截图。[审核要求](https://partner.steamgames.com/doc/store/review_process) 明确截图应来自玩法。

导出时按 [商店图形资产模板](https://partner.steamgames.com/doc/store/assets/standard) 和 [库图形资产](https://partner.steamgames.com/doc/store/assets/libraryassets) 核对每类尺寸、文字及裁切要求，不用同一横图硬拉伸全部版式。建议先做一份主视觉再派生胶囊、库封面、图标，缩小后复查标识可读性。商店宣传图不改变 05 的游戏内资产数量。

## 7. 生成式 AI 内容与第三方资产记录

按最终发行内容填写 Steam Content Survey。使用 AI 生产并随包提供给玩家的美术、声音、剧情或本地化属于需说明的制作内容；本作的候选 ImageGen 人物/背景走制作阶段预生成流程。仅写程序的效率工具与玩家实际消费的生成内容分别登记，不把游戏内没有的实时 AI 服务写成产品功能。[官方 Content Survey](https://partner.steamgames.com/doc/gettingstarted/contentsurvey) 是披露范围依据。

参考 highschool 的 `production/AI_CONTENT_DISCLOSURE.zh-CN.md` 和 `asset-provenance.csv` 方法：每件正式资产保留 ID、原始来源、工具/实际可核实模型、生成/修改日期、提示与参考图记录、编辑步骤、许可证/许可证据、发行文件哈希、审核结果及用途。第三方素材的具体作者、包名、许可证与来源以 09 的准入链为准；仓库代码 MIT 不为其中媒体资产提供统一授权。

只有已通过审核的文件进入 Player。生成草稿、同一人物的弃用版本、参考工程项目专用图和许可未核实资产不参与发行包。建议随包 `THIRD_PARTY_NOTICES`、必要许可证文本和适用的 AI 内容说明，保持它们与真实依赖/素材一致。

## 8. 从可玩包到上架的工作节点

1. 用户或发行主体完成 Steamworks 注册、实体/银行/税务资料与真实 AppID。当前没有核实本产品后台、付款或账户状态。[官方开户流程](https://partner.steamgames.com/doc/gettingstarted/onboarding?language=english) 与 [Steam Direct 费用](https://partner.steamgames.com/doc/gettingstarted/appfee) 用于后续后台操作；费用、等待期以届时后台和官方说明为准。
2. 准备商店文案、真实功能、图形素材与内容调查，提交商店审核并安排 Coming Soon 展示。当前官方开户说明要求 Coming Soon 至少两周；费用后的发行等待期也纳入排期，不在本稿承诺日期。
3. 从源码生成接近最终版本的 Windows 包，完成离线与 Steam 安装验收，配置 depot、启动项及测试分支。
4. 需要的平台可选功能分别验收；补齐来源、披露、设备与存档异常记录，然后提交构建审核。
5. 商店和构建均就绪、等待条件满足后，选择实际发行时间；发布后的反馈、版本回退和存档兼容继续沿 10 的记录方法维护。

官方 [审核流程](https://partner.steamgames.com/doc/store/review_process) 分商店与构建两部分，通常列 3–5 个工作日，并建议至少预留 7 个工作日。此为当前页面说明，不能当成项目保证审核期限。

## 9. 发行验收

- **STEAM-A01 安装启动**：Steam 下载的 Windows 包可启动、退出、重装并保留用户存档；没有依赖编辑器或外部生成服务。
- **STEAM-A02 离线与输入**：离线完成主循环；直接手柄和 Steam Input 各通过必要页面、断连、失焦及覆盖层场景。
- **STEAM-A03 版本与包**：BuildID、提交、内容/参数版本和哈希对应；正式包不含开发凭据、生成草稿或未使用资产。
- **STEAM-A04 保存**：TECH-A01 至 A06 通过；若声明 Cloud，再验证双机、账号、断网与冲突，恢复不能重复奖励。
- **STEAM-A05 商店一致**：语言、功能、系统需求、截图与实际 Player 一致，所勾选特性有验收证据。
- **STEAM-A06 来源披露**：实际资产清单、许可证、AI 内容说明和 Content Survey 对齐，所有正式素材可追溯。

这些是未来放行条件，没有“已上 Steam”“已通过平台审核”或实际构建验收记录。本轮完成的是发行技术与制作准备方案。
