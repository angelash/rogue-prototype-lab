# 套圈改造摊：开发流程、技能与能力管理

版本：v0.4；日期：2026-10-09（Asia/Shanghai）。状态：开发准备与缺口审计；已有隔离工具探针和可运行准备检查，未创建 Unity 游戏工程、安装软件或发布。

## 1. 用户决定与本轮建议

**用户已选定**：采用当前本地已有 Unity 版本，目标为 PC 单机游戏，后续面向 Steam；借鉴本地 `world-of-claudecraft` 的可用方法，补齐本项目开发能力与文档；后续开发全部由助手处理。版本、编辑器路径、模块和工程状态的基线以 [08 技术方案](08-unity-pc-technical-plan.md) 为准，新增能力实测见 [审计证据](../../../../../sources/references/development-capability-audit-2026-10-09.md)。

**助手建议**：使用“任务包 → 小范围实现 → 定向验证 → 阶段 QA → 事实记录”的循环；把纯规则与 Unity 输入、表现、存档适配分开；建立两项仓库技能，复用项目权威文档；在集成时检查语义而不只检查文本冲突。这些是开发组织方案，不是额外的游戏机制，也不是用户已经批准的排期。

**本轮范围**：检查内容与能力不足，补规格、技能路由、准备检查和隔离探针。助手承担程序、关卡数据、剧情、模型/图片/UI、音频、测试修复、构建和发行材料，不把未制作内容退回用户。后续实际开发任务的必要步骤应连续完成，不为每个阶段重新设置人工批准。实际身份、签署、付款与平台后台是外部工作条件；实现、安装、提交和对外发布仍按当前任务及已有授权判断。

## 4. 一个开发任务包需要写什么

小任务可以把以下信息写进当前任务记录，无需每次创建三份计划文件。跨会话工作再保存一份简短实施计划、进度与接续记录；文件数量按实际必要性决定。

1. **任务与授权**：用户要求的具体结果、涉及原型、允许执行的动作和既有约束。标明设计、只读检查或实现；不从素材请求推导额外机关。
2. **现状与证据**：已有代码/文档/素材、已复现问题、工作区相关改动。用稳定路径与版本，不只记录某次容易变化的行号。
3. **行为合同**：输入、输出、状态所有者、失败/重复处理、对应需求与验收。需要更改规则时先标明改动原因，不能只写“优化手感”。
4. **范围与接口**：本次改哪些职责，与 UI、剧情、保存和资产怎样衔接；哪些现有行为应保持。识别明确的阻塞问题，普通实现选择自行解决。
5. **完成证据**：定向测试或人工场景、可运行的验证入口、真实截图/日志/构建、预计需要记录的配置版本。
6. **接续信息**：已完成项、实际未完成项、失败原因、下一步最小动作。没有证据的检查标未执行，不把待做命令写成通过。

任务包示例：验证“最后一圈先完成处置再判配额”。输入是冻结场景、最后一个圈和命中结果；状态由投掷与经济事务负责；输出是处置后收据及一次结算；覆盖兑现达标、留场未达标、合法残值补齐、补圈窗口与中断恢复。UI 显示只订阅提交结果，不拥有第二套结算公式。

## 5. 模拟隔离与 Unity 接入

采用 08 的实际工程结构。建议将投掷、接受区判定、机关作用、奖品物权、双账和局流程放入可直接验证的纯 C# 规则层；Unity 输入、资源与画面经适配层读状态、发意图、表现已提交事件。具体类名、程序集和文件边界在实现前结合现有工程决定，不先把架构图当作已存在源码。

规则层不依赖场景查找、动画完成回调、墙钟时间、随机 UI 点击或 Steam 回调决定命中与奖励。正式局、练习和回放共用同一模拟，经济写入资格由模式明确控制。输入量化、固定步、随机种子、同刻事件与数值精度依据 04、06、08，不采用参考仓的 20 Hz。

Unity 可以负责展示插值、对象池、声音、粒子和 UI 焦点，但关闭这些表现不改变圈数、耐久、判定和现金。碰撞与机关轮廓以规则配置为准，不能因为精美贴图或动画摆动自动改变接受区。

配置与内容采用版本化数据源，运行、编辑预览与回放读取同一份内容。派生图集、清单或导入缓存从源资料生成；需要手工调参时修改真正的源数据，并记录受影响模板，不维护一份只供 UI 使用的“近似价格”。

## 6. 阶段 QA 与完成证据

验证由同一协调者统一执行，独立审阅者只检查所分配内容及共同结果，避免多人同时跑耗时 Unity 构建或修改同一自动生成文件。只读审阅报告可以给出修复建议，不能直接改别人负责的文件。

### Q0：文档、技能与环境准备

检查引用、术语、来源、任务边界、现存工具及技能 frontmatter。已建立 [准备检查入口](../../../../../scripts/README.md)：环境清单与文档/源文件哈希可实际运行；两技能另用现有 `quick_validate.py` 验证。Blender 导出/渲染、单个参考 GLB 读取和音视频编码探针见审计证据。报告“文档检查通过”“隔离样件通过”与“游戏运行通过”是不同结论；本轮没有 Unity 工程与构建结果。

### Q1：基础规则原型

对应 07 的原型门槛。优先验证稳定输入、命中边界、两种基础机关、互斥处置、重复事务和最后一圈顺序。建议使用纯逻辑测试与少量真实场景观察；实际运行器在工程建立后核对，不照搬 Vitest 命令。

### Q2：一章纵切

把准备、投掷、处置、成功/失败、商店、跨摊与恢复接成可玩的四摊。检查键鼠与手柄、UI 焦点、素材与事件对应，以及不重复发奖。至少保留一份实际桌面运行证据；在编辑器里无报错不等于桌面版本已可用。

### Q3：内容与集成

按 13 审核十二模板、全部合法解锁/预装覆盖与可达证据、六机关/三圈资产映射、正式文本键/条件和各项辅助设置。先计算离散组合规模与连续状态的等价依据，采用同一 Core 验证，不以边界抽样冒充全覆盖。规则变更先跑相关回归，再重审受影响模板；纯装饰修改用视觉与引用核验，不为每张图片编写重复的逻辑测试。

### Q4：候选发行包

依据 11 核对实际 Windows 桌面包、干净环境启动、操作与存档路径、缺失资源、素材许可及商店描述。只在实际构建和适用平台流程完成后标记候选包；上传、审核和对外发行分别记录真实状态。

每次 QA 报告包含范围与基准、构建/配置版本、运行过的检查和退出结果、已确认问题、已修复项、未验证部分与结论。建议结论为“符合当前任务范围”“符合但有明确待验证项”或“仍有阻塞”；不能因为全仓其他原型尚未制作，把某次已完成的文档任务写成失败，也不能因文档完整宣称游戏完成。

## 7. 记录与交接模板

阶段记录最小字段：`taskId`、日期、任务目标、需求/文档版本、相关提交或工作区状态、Unity/构建版本、参数/内容版本、验证方式、实际结果、缺口、下一动作。字段可以先使用中文 Markdown，不为记录本身创建数据库。

缺陷记录：触发步骤、期望与实际、种子及输入、模式、事件/事务编号、证据路径、影响、定位职责、修复与回归结果。金额与机关状态读真实事件，不能用“运气不好”替代根因。

素材记录按 09 的权威清单，任务记录只引用资产 ID、版本及验收状态，不另建一份价格/功能映射。正式试玩记录遵循 07，保留匿名样本、设备、辅助设置与配置版本；主观喜好和规则缺陷分开记录。

恢复任务时先看最后验证通过的状态，核对当前文件与当时版本，再执行下一最小步骤。若并行修改或上游集成改变了假设，更新接续点；不能按旧计划路径继续，把已经移走的职责再写一遍。

## 8. 语义集成检查

只有实际发生集成或重叠修改时采用此流程，不为普通文案工作新建强制分支策略。

比较相互影响的修改意图及最终路径，重点检查：机关注册和资产 ID 是否遗漏、同一判定是否出现两份、旧现金资格是否被新字段默认值覆盖、故事事件是否重复发奖、存档字段与迁移是否仍兼容、内容模板是否还符合新版参数。

对确认的回归先保留可复现证据，再按用户已授权范围修复；只读请求只报告。自动生成资产以权威源重新生成，不靠随意拼接两份产物解决冲突。重新验证受影响行为即可，除非出现新失败或剩余风险，不反复跑无关全量检查。
