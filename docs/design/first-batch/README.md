## 范围与决策归属

用户本轮要求：汇总标星优先项目，追加“贪吃蛇孵化场”，整理为第一批要做的项目；为每个项目建立独立目录、需求文档和设计文档，并提交。

本地工作簿的单元格文本未找到直接星号标记。现有正文明确推荐 032、013、051，并重点观察 121、126。本次据此把前五项映射为“标星优先”范围，再加入用户明确指定的 027；这一名单映射是助手依据资料作出的解释，不记录为用户逐项确认了五个编号。来源、定位与筛选理由见 [筛选登记](../../../sources/chatgpt/first-batch-selection.md)。若用户另行指定标星名单，以新决定更新本批范围。

第一批是优先准备与后续验证的项目集合；用户已要求先开始 013，其余五项实际开工顺序尚未指定。用户后续要求其余首批逐个按规范开发，每完成一项提交；当前助手采用既有建议顺序032→051→027→121→126，阶段按各项目首次纵切拆分，不追认用户曾指定这一排期。正常输入暂受系统安全权限提示阻挡的项目如实记录欠据，独立候选实现/测试/构建与备份继续；不表示体验假设已成立。

## 六个项目

### 032 回转寿司工坊

来自原首批推荐。有限工位、盘位与顾客离席窗口可以直接产生工序和交付时机的冲突；优先检验同样的切分站是否在不同订单下值得保留或拆掉。

历史v0.1最小范围为二维单环、6站位、6料理状态、4加工站、2类订单、固定步数；v0.2首次候选用三维厨房呈现同一离散单环，见[专属合同](../../../prototypes/proto-032-sushi-workshop/DEVELOPMENT.md)。先验证加工、数量守恒与交付，再做订单对照。

[项目目录](../../../prototypes/proto-032-sushi-workshop/README.md) · [需求文档](proto-032-sushi-workshop/requirements.md) · [设计文档](proto-032-sushi-workshop/design.md)

### 013 套圈改造摊

来自原首批推荐。奖品可以兑现，也可以成为改变下一投的机关，能把技术动作与当前现金/后续能力的取舍连接起来。

历史 v0.1 最小范围为二维侧视或固定平面、1 基础圈、2 机关、6 奖品位；用户后续改为真实三维斜视、玩家近处向地面两排六槽抛圈。当前继续验证基础投掷、兑现和留场，现行合同见 [项目开发要求](../../../prototypes/proto-013-ring-toss/DEVELOPMENT.md)。

[项目目录](../../../prototypes/proto-013-ring-toss/README.md) · [需求文档](proto-013-ring-toss/requirements.md) · [设计文档](proto-013-ring-toss/design.md)

[完整方案入口 v0.6](proto-013-ring-toss/full-game/README.md)：完整蓝图、Unity PC/Steam、16 项开发缺口、内容生产和验证合同。用户明确选择现有 Unity、PC 单机、Steam 目标和真实三维斜视地摊，并由助手承担后续开发；旧固定正交 2.5D 建议保留为历史，具体内容、造型、镜头参数与数值仍是实施建议。保留最小原型验证门槛，再推进一章纵切。

### 051 回收保洁队

来自原首批推荐。吸入物占容量，同时可以出售或转成清洁剂，适合检验路线、处理顺序和资源用途之间的因果。

最小范围：单房间、3 污物、2 回收材料、2 刷头、1 滤芯。先关闭升级比较布局与容量，再加入转换滤芯。

[项目目录](../../../prototypes/proto-051-recycling-cleaners/README.md) · [需求文档](proto-051-recycling-cleaners/requirements.md) · [设计文档](proto-051-recycling-cleaners/design.md)

### 027 贪吃蛇孵化场

用户明确追加。身体长度既提供功能又占空间，断尾同时改变主蛇能力和采集方式，适合验证玩家是否会主动保持短体或回收分身。

最小范围：离散网格、1 主蛇、至多2 分身、3 身体节、2 简单分身行为。先验证基础蛇与能力占位，再引入一次切尾，最后启用第二分身。

[项目目录](../../../prototypes/proto-027-snake-hatchery/README.md) · [需求文档](proto-027-snake-hatchery/requirements.md) · [设计文档](proto-027-snake-hatchery/design.md)

### 121 磁铁拾荒者

来自新增重点观察方向，本轮并入第一批文档。货物直接改变磁铁几何与下一次可达集合，能以少量形状验证工具和收益的互斥用途，不需另建磁场物理。

最小范围：离散网格、4 形状、固定接点、首件吸附、公开承重与有限电量。关键观察是主动拆短，而非越长越好。

[项目目录](../../../prototypes/proto-121-magnet-scavenger/README.md) · [需求文档](proto-121-magnet-scavenger/requirements.md) · [设计文档](proto-121-magnet-scavenger/design.md)

### 126 收割机自己铺路

来自新增重点观察方向，本轮并入第一批文档。收割改变通路，秸秆续航与铺路争载货空间，适合验证订单和工具是否真正改变路线。

最小范围：10×10 田地、3 地块、3 模块、3 轮订单、固定行动预算。重点约束是补油增加续航却不延长截止。

[项目目录](../../../prototypes/proto-126-harvester-paths/README.md) · [需求文档](proto-126-harvester-paths/requirements.md) · [设计文档](proto-126-harvester-paths/design.md)

## 建议推进顺序

历史助手建议按 032 → 013 → 051 → 027 → 121 → 126 串行验证。用户后来要求先开始 013，当前已进入该项目 P0；其余五项现已授权串行推进，助手采用上述顺序中的032→051→027→121→126，不写作用户逐项指定。027 的身体与分身、121 和 126 的几何与路线构筑仍按各自合同验证。

每项先得到能复现的基础动作与反馈，再加入核心取舍，最后进行删除规则对照。一个项目遇到停止条件时先留下原因与证据，再决定重做或切换项目；不以完成整套内容作为单项成功标准。

## 文档与目录约定

`prototypes/proto-<原方案编号>-<名称>/` 是每个项目的独立实现入口，根 `DEVELOPMENT.md` 归档专属准备、要求、验收与真实落地，README 链接共同规范、该合同及需求设计。权威设计正文按项目分目录保存在 `docs/design/first-batch/`，符合既有归档约定，不复制两套会相互漂移的正文。

每个需求文档说明体验目标、最小范围、必须功能、可观察验收和停止条件；每个设计文档说明状态、动作、结算、异常处理、反馈与验证路线。来源原规则与新增草案分别标明。需求中的验收场景是要求；实际通过范围与证据在各项目 `DEVELOPMENT.md` 登记，013 的 48 项结果不代表其全部需求或其它项目通过。

试玩时在 docs/playtests/ 为对应编号留下场景版本、输入、关键行为、误解、主动改变、失败归因和下一次尝试计划。当前全部项目继承共同开发基线，专属覆盖与具体数值、美术、镜头仍分别记录；不预建适配全部项目的通用肉鸽引擎。

共同方法见 [设计原则](../01-design-principles.md) 和 [研发方法](../05-development-method.md)。历史三项推荐及范围见 [原验证计划](../03-prototype-validation-plan.md)；本轮决策见 [决策记录](../../decisions/decision-log.md)。
