# 032 回转寿司工坊：首次可玩纵切实施方案

版本：v0.2；日期：2026-10-10（Asia/Shanghai）；任务开始：2026-10-09。状态：首次可玩候选实现，Unity Prepare、30项规则/存储测试与已完成普通Mono Strict构建通过；最终字体位置调整后重建与原生操作仍待补，未完成完整纵切验收。分项事实见 [开发记录](2026-10-10-slice-01.md)。

## 1. 用户决定、原案与当前取舍

用户已授权另外五个项目逐个开发；本轮助手采用各项目合同的首次可玩纵切范围推进，当前只做032，完成本项目并提交后再进入下一项。共同基线为 [DEVELOPMENT_STANDARD.md](../../../DEVELOPMENT_STANDARD.md)：已安装Unity2022.3.62f3c1、Windows x64 PC单机、面向Steam的制作准备。当前不包含完整Steam接入/上传或发行。

依据为 [需求v0.1](../../design/first-batch/proto-032-sushi-workshop/requirements.md)、[设计v0.1](../../design/first-batch/proto-032-sushi-workshop/design.md) 与 [项目开发合同](../../../prototypes/proto-032-sushi-workshop/DEVELOPMENT.md)。原案032，工作簿与筛选定位保留在原需求，不覆盖旧版本。

本轮助手实施建议：以三维斜俯视小厨房展示二维单环的离散六槽规则，只有一个固定场景、六料理状态、四加工站与两类互斥订单。三维厚度、灯光和运盘动画不增加自由驾驶、任意布线、真实切菜物理、员工经营或其它站位。

两订单的“对照”采用同一初始场景分别开轮，每轮只有一种主要订单；切换订单重置到相同初始资源，不把两种需求同时塞进一轮，也不让前轮盈利污染对照。数值、料理/工站身份、胜负和补救由本项目Core同一配置所有。

## 2. 参数与内容所有权

资金、传送步限、盘库存、原料/工站/改站/清洗/转卖价格、两订单需求/数量/等待/报价，以及胜负/补救均为v0.2初期建议，不是已验证的平衡结论。它们由规则负责代理在本项目Core冻结；UI、作者预览、存档、自动检查与文档都引用同一规则版本，不建立另一份可编辑参数副本。

权威配置为 [Rules.cs](../../../prototypes/proto-032-sushi-workshop/game/SushiWorkshop/Assets/SushiWorkshop/Core/Rules.cs)，命令/结算/快照为 [Session.cs](../../../prototypes/proto-032-sushi-workshop/game/SushiWorkshop/Assets/SushiWorkshop/Core/Session.cs)，说明为 [Core README](../../../prototypes/proto-032-sushi-workshop/game/SushiWorkshop/Assets/SushiWorkshop/Core/README.md)。已只读核对规则版本 `0.2.0`、快照格式 `1`；下面是该配置的初期建议摘要，文档不是第二套可编辑配置。实现与摘要不一致时先核对配置并修订摘要，运行结果使用真实状态的整数金额、份量、步骤与订单剩余量。

- 一轮六槽、六实体盘、十八传送步；每六步圈边界。入口为槽0，沿递增槽号移动，顾客在槽5；初始工站为槽1添料、槽2卷制、槽3加热、槽4切分。
- 初始资金18；投一份原料花3；洗一盘花1；搬站花2；买站花6；转卖站收3；每轮四次调整额度，由搬站、买站、转卖共同消耗。整份料理含2食材单位，小份含1单位。
- `WholeHeated` 高价整份订单：`HeatedRoll` 整份两盘，每盘10，等待十八步。`QuickSmall` 快速小份订单：`SmallRoll` 小份两盘，每盘7，等待十二步。两订单互斥，每轮只选一类。
- 十八步统一结算：主订单达成为订单成功；否则按食材单位1收款的基础出售累计收入达到6判降级经营成功；两者皆未达则失败，转卖收入不计入基础门槛。弃单罚2。订单完成/十二步离席只改变订单状态，整轮继续；最后一步先处理合法交付，再离席/结算。

六状态身份为 `RiceBase`、`FilledRice`、`Roll`、`HeatedRoll`、`SmallRoll`、`SmallHeatedRoll`；对应四工站 `Filling`、`Rolling`、`Heating`、`Cutting`。规则定向测试已通过，金额、步限与恢复门槛仍需后续平衡与玩家对照，不把候选报价称为已平衡。

稳定内容身份至少区分六站槽、四工站、六料理状态、盘ID、订单ID和事件序号。展示皮肤与规则身份分别登记；一只盘不能同时在环、待入口、干净库存和脏盘区。

读取/命令合同：`Session.CreatePrototype(OrderKind)` 建立独立初态，`Retry()` 重试当前订单；`State` / `ExportSnapshot()` 返回防外部修改的完整状态副本。`StartOrResume`、`Step`、`LoadIngredient`、`WashOne`、`MoveStation`、`SellStation`、`BuyStation`、`SetDeliverable`、`QueueBaseSale`、`AbandonOrder` 均返回 `CommandResult`，可带幂等命令ID；UI不得直接修改State或重复播放恢复后的奖励。改变订单建立另一 `CreatePrototype`，不跨订单带财务。

Core槽号是0–5，画面/数字键编号是1–6，UI编号=Core槽号+1。两条独立推导对照已由本轮规则测试复核：整份订单将切分站从Core槽4移到槽0（画面5→1），初投一份，第5步交付；第6步边界再投一份，第11步交付，十八步结算钱包30。小份订单将加热站从Core槽3移到槽0（画面4→1），初投一份，第4步切分，新盘第5步进入且不加工；原盘第5步、新盘第10步交付，十八步结算钱包27。两轮均从18资金和六干净盘重新开始，除列出动作不额外投料/改站。SUS-A01–A05及保存对应定向测试通过，黄金输入仍只是规则基准，不证明最佳策略或乐趣；原生键鼠复现尚待解除系统弹窗后验证。

## 3. 第一版完整循环

1. 选高价整份或快速小份订单，读取需求/目标/离席窗口及初始资源。
2. 在合法准备窗口选择/购置/移动/转卖工站，逐盘设可交付、保留或基础出售。付费投料与清洗可在任何合法单步安全点操作；连续运行先暂停，仍须资金、干净盘和入口容量满足。
3. 单步或连续推进同一离散规则。每步结束画面呈现已提交加工、交付、阻塞和成本，不从动画结束时间算第二次步骤。
4. 到圈边界返回配置/调标窗口；保留盘继续占位，脏盘须付费清洗才可投料。运行中禁止改站、调交付/基础出售标记和弃单，投料/清洗仍是合法单步间的付费动作。
5. 订单达成或离席后显示状态变化，保持十八步统一结算；圈边界仍可做合法基础补救。步限结束显示目标、交付、收入/支出、保留/阻塞/超时原因。
6. 可重试该订单，或切到另一订单以相同初态对照；恢复只继续所存一轮，不重新抽单或返还消费。

每步共同次序是开始快照 → 所有旧盘前移一槽 → 按稳定槽/盘身份加工 → 检查可交付与份量 → 基础出售等已安排动作 → 等待减少/离席 → 圈边界或结束。加工与顾客点同槽时先加工后交付；最后一步合法交付先计入再判截止。

切分先确认额外干净盘与单盘暂存容量/环容量，再将总食材分给两盘。新小份本步不再次前移/加工，继承原交付及基础出售标记；下一步旧环盘移动后，入口空才进入，也不在进入当步加工。条件不足时保留原盘/原料理且不额外扣材料。交付后实体盘变脏，不能直接重新投料。

## 4. 失败与补救合同

胜负、目标与等待取Core配置；顾客不接受错状态、错份量或保留盘。资金不足、盘/入口满、阶段非法的动作整体拒绝，并显示具体缺口；无借款、隐藏成功概率或自动纠错。

基础出售、弃单和工站转卖提供有代价的应对，不承诺所有失误都能转败为胜。基础出售须在准备窗口给具体盘预先打标，盘到顾客点才收款：匹配且可交付的主订单优先；未被订单接收时才按基础标记出售，回收后盘变脏。保留标记阻止主订单接收，若主动安排基础出售仍可能出售，不能把“保留”解释为拒绝一切回收。弃单不自动出售库存、不退消费，且仍须达到基础收入门槛。转卖可回资金但减少工站和调整额度；单靠卖站不能取得基础经营成功。

核心缺站样本必须显示上述补救条件和结果；不能靠重开自动还钱。具体动作由Core合法性与费用核定，未实现路径不能显示为已可用。

准备操作、连续运行、单步、保存、恢复、重试和订单切换各有一个命令所有者。一次真实输入只提交一次，失败不先改模型/钱包再撤销。

H打开关键事件复盘并暂停连续推进；显示最近十条加工、切分、切分阻塞、拒收、离席、交付的步骤/盘/槽和原因，H或Esc关闭。复盘只消费已提交事件，不提交加工/经济命令，关闭后须主动续跑。实际面板/输入隔离由窗口QA核对，不能用事件数组存在代替玩家看得到原因。

槽锚点、盘位置和加工状态从规则读取，三维沿轨插值只供展示；Mouse选槽返回稳定ID，仍经阶段校验。俯视斜角须看清环方向、全部六槽、盘份量/标记、输入/交付点及工站，不能靠诊断文字堆叠才能理解。

## 6. 安全点保存与恢复

保存完整的一轮状态，不只保存资金：配置/格式/内核版本、订单选择与剩余需求/等待、运行步/圈边界/阶段、站配置/改站预算、资金、盘ID/位置/料理/份量/交付标记/归属、干净与脏盘/待入口库存、事件/命令身份及一次性处理记录。

只在已提交的离散安全点写入；运盘动画期间先完成当前规则步再保存，UI动画不能成为半步真值。恢复重新校验引用、容量、数量与版本，回到对应安全状态，不重复加工/交付/清洗、不还原料/钱、不重置等待或换订单。

磁盘适配保留上一份有效备份并采用可验证的完整快照提交；写失败保持当前内存与有效旧档，显示重试/返回等合法动作。未知格式、坏档和无有效备份分别提示，不静默开新局覆盖。隔离测试覆盖提交前/后中断、损坏、重复请求与恢复后继续同序列；不破坏真实存档。

Core以 `ExportSnapshot()` → `RoundSnapshot` / 静态 `TryRestore(snapshot, out Session, out string)` 导出与校验纯数据。恢复从初态重放保存的生产命令，逐项比较完整状态和事件；恢复本身不新增命令/奖励，并清空 `LastEvents`，避免重新消费声音/交付事件。磁盘由 `PrototypeKit.CheckpointStore<T>` 负责：格式版本、完整payload与SHA256封装，Save先校验新快照的领域合法性，再写 `.pending` 和提交 `session.json`；替换前对旧主档做摘要和领域状态校验，只有合法旧主档才更新 `.bak`，损坏主档不能覆盖唯一有效备份。读取只回退到通过格式/摘要/状态校验的备份。非法新档拒绝、备份保护和隔离故障对应八项存储测试已通过，结果见开发记录；实际窗口保存/退出仍待补，不能据此宣称所有断电条件已验证。
